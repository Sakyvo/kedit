## Problem

为 Author 解决：约 80 万字 / 2MB 的超长 Document 在 2018 年中端机
（Honor Magic 2，Kirin 980）上**打开即卡死**、**移动端输入延迟大**。
代码已定位病灶：打开时全量 Prism 高亮 + 全量 markdown-it 转换 + 全量预览 DOM
构建 + 全量尺寸测量同步串行；击键路径每次做 O(全文) 三件套（全文 textContent
读取、全文 diff、全文重解析分节），且预览面板隐藏时（移动端常态）预览渲染与
测量照跑不误。验收目标：打开 1 秒内可输入（"像打开记事本"）、移动端击键流畅。

## Decisions

架构决策与被否方案见 `.docs/adr/0012-segmented-large-document-pipeline.md`。要点：

- **文本模型与 DOM 分离**：全文字符串模型是唯一事实源（编辑/撤销/查找替换/
  Sync/持久化都落在模型上）；DOM 降级为可重建的渲染产物。击键以 delta 写模型，
  击键路径不再有任何 O(全文) 操作。
- **分段单位 ~2 万字、段落边界落刀**（拒绝硬切第 20000 字：段中截断破坏高亮/
  渲染，插入位移导致后续全段判脏级联重刷）。80 万字 ≈ 40 段。
- **编辑器渐进载入**：首段同步渲染达成 1 秒可输入；其余段空闲时间分批补齐
  （终态 = 全量 DOM）；未载入段为**空占位**（估算高度），滚动/点击到达即载；
  尺寸测量 O(1) 增量。
- **预览不可见即零渲染**（设备无关）：隐藏时零转换、零 DOM、零测量、零
  textToPreviewDiffs；可见时从当前位置分段渲染、空闲补齐；连续输入期间可见
  预览降频（停笔 ~200ms 才刷新）。含引用定义的文档回退全量转换。
- **TOC 独立行扫描**构建，与预览渲染解耦，打开即全量。
- **缺陷弥补走模型层**（空占位的代价在此补偿）：内置查找替换 = 全文搜索；
  Ctrl+A 全选复制/剪切一律由模型供全文（**硬性验收项**）。浏览器 Ctrl+F 与
  拼写检查对未载入段降级，接受。
- **用户逃生开关**：设置项「长文档分段加载」（`segmentedLoading`，默认**开启**），
  位于 配置 → 可视化、「常规」上方（新建「性能」组）；关闭后回退旧全量管线。
  双路径并存是有意的安全带，真机长期验证合格前不拆。
- 编辑完整性红线：已载入段内编辑体验与现状逐字节一致（原生回显、块级重高亮、
  撤销链）；开发模式下断言「分段 DOM 文本 ≡ 模型切片」做对账哨兵。

## Out of scope

- 编辑器窗口化/虚拟化（DOM 永久只存可视区、远段卸载）——真机验收不达标再议（乙案）。
- markdown-it / Prism 迁 Web Worker。
- 纯文本降级模式（Author 明确拒绝：高亮必须保留）。
- Publish / pdir 管线、导出管线（本就是全量渲染，不受分段影响）。
- 滚动同步精度的提升本身（未测量区维持估算退化，不追求完美）。
- 滚动条占位跳动的彻底消除（接受先估算后修正的轻微跳动）。

## Testing strategy

- Jest 测试链已断（项目 AGENTS.md），唯一 CI 门槛 = `npm run build` 通过。
- 自动化哨兵：开发模式下模型↔DOM 对账断言（分段文本逐段等于模型切片），
  不一致即抛错——编辑完整性的第一道防线。
- 打点数：打开首段可输入耗时、击键路径耗时（移动端 profile 用）。
- 真机验收（Honor Magic 2 + 真实 80 万字文档，Pages 部署后）：打开 <1s 可输入、
  击键流畅、滚动/查找/全选复制/撤销/IME/同步 全通过；全载后的长期滚动流畅度
  是真机裁决项。
- 桌面回归：普通文档全部交互（撤销/查找替换/粘贴/图片/讨论）、双栏预览实时性、
  Publish；关闭开关回退路径验证。
- 手工验收清单随最后一张卡交付；验收类卡以 `review` 状态交接，不阻塞主线。
